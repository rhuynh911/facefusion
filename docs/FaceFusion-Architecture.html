Section 1

System Overview & Technology Stack

FaceFusion is a face-manipulation platform built around ONNX Runtime for portable, hardware-accelerated inference. It performs face swapping, enhancement, editing, age modification, lip-syncing, colorization, upscaling and more, driven either through a command-line interface or a Gradio web UI. The same processing core serves both.

1.1 Design principles

  • Plugin-oriented processing. Every transformation (swap, enhance, edit, …) is a self-contained processor module conforming to a fixed 8-method interface, loaded dynamically by name.
  • Model-agnostic inference. A central inference_manager pools ONNX sessions; execution providers (CUDA, TensorRT, DirectML, …) are auto-detected and prioritized at runtime.
  • Shared analysers. Face detection, landmarking, recognition, classification and masking are computed once per frame and reused by all processors through a content-hash cache.
  • Reproducible jobs. Every run — interactive, headless, or batch — is expressed as a persisted JSON job of ordered steps, giving identical execution semantics everywhere.
  • Dual state contexts. CLI and UI keep separate state buckets, auto-selected by call-stack inspection, with explicit sync bridges.

Section 2

Entry Point & CLI Dispatch

The single executable facefusion.py defers to core.py::cli(), which builds the argument parser, validates it, applies arguments into global state, and routes to a command handler. All heavy commands pass through a two-stage pre-check before any model runs.

2.1 The cli() bootstrap

The bootstrap sequence in core.py:23–40 is deliberately linear:

def cli():
    if pre_check():                        # python>=3.10, curl & ffmpeg on PATH
        signal.signal(SIGINT, signal_exit)  # graceful Ctrl-C
        program = create_program()          # compose all sub-parsers
        if validate_args(program):          # defaults must be valid choices
            args = vars(program.parse_args())
            apply_args(args, state_manager.init_item)   # seed BOTH cli+ui buckets
            if state_manager.get_item('command'):
                logger.init(...); route(args)
            else: program.print_help()
        else: hard_exit(2)
    else: hard_exit(2)

pre_check() — environment

  • Python < 3.10 → error & abort (core.py:95)
  • curl missing on PATH → abort
  • ffmpeg missing on PATH → abort

common_pre_check() — models + safety

  • pre_check() on all shared analyser modules (download hashes/sources)
  • Re-hashes content_analyser.py source; must equal b14e7b92 (see §10.1)

2.2 Command routing

route(args) (core.py:43) dispatches on the command state item. It first applies an optional system-memory limit, then branches:

Error-code convention Workflows return a small integer ErrorCode: 0 success, 1 generic failure, 2 pre-check/validation failure, 3 content-analysis rejection (NSFW), 4 user-initiated stop. hard_exit(code) propagates it to the shell.

Section 3

Program, Arguments & State

Three modules translate the outside world into runtime configuration: program.py defines the CLI, args.py bridges parsed arguments to state and to persisted jobs, and state_manager.py holds that configuration in two parallel contexts.

3.1 Program composition

program.py builds the CLI from many small, single-topic ArgumentParser factories, each created with add_help=False so it can act as a reusable parent. Two aggregators bundle them:

collect_step_program()
detector + landmarker + selector + masker + voice-extractor + frame-extraction + output-creation + processors
collect_job_program()
execution + download-providers + memory + log-level

create_program() then registers one sub-parser per command (run, headless-run, batch-run, all job commands, …), composing each from the relevant parents. Two behaviours are worth noting:

  • Config-backed defaults. Each argument's default comes from config.get_*, i.e. from facefusion.ini, falling back to a hard-coded string.
  • Key registration as a side-effect. Building a factory also calls job_store.register_step_keys([…]) or register_job_keys([…]). This registry is the single source of truth for which keys are per-step vs job-wide.
  • Dynamic choices. The detector-size choices depend on the chosen detector model (a preliminary parse_known_args reads it first); processors inject their own arguments via register_args.

program_helper.validate_args() walks the whole parser tree and verifies that every argument whose default is constrained by choices actually holds a legal value — catching a misconfigured INI before anything runs.

3.2 Argument ↔ state ↔ job bridging

args.py::apply_args(args, apply_state_item) is the args→state writer. Crucially it takes the state-writer as a parameter, so the same code serves two callers:

CallerWriter passedEffect
CLI startup (core.py:30)state_manager.init_itemSeeds both cli & ui buckets from argv
Per-step (core.py:327)state_manager.set_itemApplies one step's merged args into the active bucket

Four reducer/collector helpers, driven by the job_store key registry, move data between argv/state and the persisted job JSON:

reduce_step_args(args)
argv → the subset of registered step keys (stored in a job step)
reduce_job_args(args)
argv → the subset of registered job keys (execution, memory, patterns…)
collect_step_args()
live state → step keys (UI snapshots current config into a job)
collect_job_args()
live state → job keys

3.3 Dual CLI/UI state

state_manager.py keeps a module-global STATE_SET = {'cli': {}, 'ui': {}}. The active bucket is chosen per call by app_context.detect_app_context(), which walks the call stack and inspects filenames:

init_item(k,v)
writes to both buckets (startup baseline)
get_item(k) / set_item(k,v)
read/write the active bucket only
sync_item(k) / sync_state()
copy one key / the whole bucket from ui → cli

3.4 Config & choices

config.py
Wraps facefusion.ini via a singleton ConfigParser. Typed getters (get_str/int/float/bool_value + get_str/int_list) return the INI value only if present and non-blank, else a cast fallback. Defaults live at the program.py call sites, not in the file.
choices.py
The single registry of allowed values: model lists (mostly derived from Literal types via get_args()), mapping dicts (provider→ORT class, mask region→label ids, encoder sets), and numeric ranges feeding both argparse and UI sliders. Keeps CLI and UI vocabularies identical.

Section 5

The Processor Plugin System

Processors are the units of transformation. Each is a subpackage under facefusion/processors/modules/<name>/ whose core.py implements a fixed interface. They are loaded dynamically by name and chained per frame.

5.1 Dynamic loading & the contract

The 45-line loader processors/core.py imports facefusion.processors.modules.<name>.core and validates that it exposes all eight required methods; a missing method raises NotImplementedError and hard-exits. get_processors_modules(names) returns the validated module objects used throughout the workflows.

5.4 Shared processor helpers

pixel_boost.py
Two numpy reshape helpers — implode_pixel_boost tiles a large face crop into model-sized sub-frames for batched inference, explode_pixel_boost reassembles them. Used only by face_swapper to swap above the model's native resolution.
live_portrait.py
Motion/expression math for the LivePortrait model family: Euler-angle limits (pitch ±30°, yaw ±60°, roll ±20°), expression clamps, and rotation-matrix construction. Powers face_editor and expression_restorer.

Model declaration & source keys

Each create_static_model_set() returns a nested dict keyed by model name; every entry carries __metadata__ (vendor/license/year), hashes, sources ( {url, path} pairs), plus template, size, and often type/mean/std. A single model may declare multiple source keys — e.g. face_swapper's face_swapper + embedding_converter, or face_editor's six LivePortrait sub-models — each becoming its own InferenceSession.

Section 6

Inference & Execution Layer

This layer turns model files into running ONNX sessions on the best available hardware, and guarantees model integrity through on-demand download with checksum verification.

6.1 ONNX session pooling

inference_manager.py caches sessions in a two-tier global INFERENCE_POOL_SET = {'cli': {}, 'ui': {}}. Each pool is keyed by an inference context string that concatenates module name, model names, device id, and the ordered execution providers:

  • Lazy & shared. get_inference_pool() waits while process_manager.is_checking(), resolves providers (a module may override resolve_execution_providers), and cross-populates the cli/ui caches so both contexts reuse one session. For multi-GPU it returns a pool for a randomly chosen device id (crude load spread).
  • Eviction. clear_inference_pool() deletes the module's contexts; on Windows + DirectML it clears the whole app-context bucket (a driver workaround, since DirectML sessions must be torn down together).
  • No central lock. The only concurrency gate around pool mutation is the is_checking() spin-wait; session thread-safety is handled at .run time (§10.2).

6.2 Execution-provider priority

execution.py derives available providers from ONNX Runtime and re-sorts them into FaceFusion's canonical priority, then maps each to an ORT (name, options) tuple. CPU is always appended last as the universal fallback.

PriorityProviderNotable options set by create_inference_providers
1CUDAdevice_id, cudnn_conv_algo_search (DEFAULT on GTX 16xx, else EXHAUSTIVE)
2TensorRTengine & timing cache paths, trt_builder_optimization_level: 4
3ROCmdevice_id
4MIGraphXdevice_id + optional model cache dir
5CoreMLSpecializationStrategy: FastPrediction + cache dir
6OpenVINOdevice_type (GPU / GPU.N), precision: FP32
7QNNdevice_id, backend_type: htp
8DirectMLdevice_id (deprioritized near the tail)
9CPUbare fallback, always last

Device discovery runs nvidia-smi --query --xml-format (cached) to populate ExecutionDevice records — driver, CUDA version, product name, VRAM total/free, temperatures, utilization. Engine/timing caches live under a version-scoped .caches/<ort-version> directory to avoid cross-version collisions.

6.3 Model download & integrity

download.py fetches models on demand into .assets/models/. URLs are resolved by walking download_providers in order — GitHub releases, then Hugging Face (with an hf-mirror fallback) — pinging each candidate base URL and using the first reachable one.

Download mechanics
conditional_download compares the existing partial size to the remote content-length and resumes via curl (5s timeout, 5 retries), driving a tqdm bar by polling file growth.
Integrity gate
Each .onnx has a sidecar .hash (CRC32). validate_source_paths re-hashes the file and, if it still fails after (re)download, deletes the corrupt source. A source is trusted only when its CRC matches.

hash_helper.create_hash() is simply crc32 formatted as 8 hex digits — an integrity/ tamper checksum, not a cryptographic hash. The same primitive underpins the content-safety gate (§10.1) and the frame cache key.

Section 7

Processing Workflows & Media I/O

Two workflow modules orchestrate the full pipeline. The image path is a short linear sequence; the video path adds frame extraction, multi-threaded per-frame processing, re-encoding, and audio restoration.

7.1 The video pipeline

workflows/image_to_video.py::process() runs an ordered task list, aborting on the first non-zero error code, bracketed by process_manager.start() / end():

Frame parallelism. process_video submits every extracted frame to a single ThreadPoolExecutor(max_workers = execution_thread_count) (default 8, range 1–32) and consumes results via as_completed; a stop request cancels the remaining futures. Each worker runs process_temp_frame, which reads the frame (RGBA), fetches the aligned audio/voice frames for lip-sync, runs every processor's process_frame in sequence, merges the mask, and writes the frame back in place.

On execution_queue_count Older FaceFusion had a separate queue-count knob; in this version concurrency width is governed solely by execution_thread_count — all frames are submitted at once and the executor's internal queue backs them.

7.2 The image pipeline

image_to_image.py is the same driver without frames: setup (NSFW check + temp dir) → prepare_image (resolve output resolution, copy into temp) → process_image (read RGBA, run every processor, merge mask, write) → finalize_image (encode to output, clean up). RGBA is used so an alpha mask can travel with the frame; processors receive the RGB slice while the mask is carried separately.

Section 8

The Job System

Every run is a job: a JSON file of ordered steps, each capturing the arguments for one processing operation. This makes interactive, headless, and batch runs share identical execution semantics.

8.1 On-disk model & status flow

A job's status is the directory it sits in under jobs_path. Changing status = moving the file. init_jobs creates one directory per status.

The JSON schema is small: a Job has {version, date_created, date_updated, steps[]} and each JobStep is {args, status} where step status adds the transient started.

8.2 Manager & runner

job_manager.py (CRUD)
  • create_job → drafted (only if id unused anywhere)
  • submit_job → queued (needs ≥1 step)
  • add / insert / remove / remix_step
  • remix_step chains a new step onto a prior step's output
  • file primitives: read/update (stamps date_updated)/move/delete; find_job_ids globs sorted by mtime = submission order
job_runner.py (execution)
  • run_job runs only queued jobs; run_steps is sequential and short-circuits on first failure
  • run_step sets started, calls the injected process_step, moves the step output
  • finalize_steps concatenates multi-step video outputs (or moves images)
  • retry_job re-queues a failed job; success → completed, else → failed

8.3 Headless & batch as ephemeral jobs

Both non-interactive commands reuse the exact same machinery via a throwaway job:

CommandBehaviour
headless-runOne ephemeral job, one step: create → add_step → submit → run in a single expression
batch-runOne ephemeral job, one step per file: expands source_pattern×target_pattern (cartesian product), formats an output_pattern with {index}/{source_name}/{target_name}/{target_extension}

job_store.py holds the {job_keys, step_keys} registry populated by program.py; job_helper.py supplies timestamped ids (job-YYYY-MM-DD-HH-MM-SS) and per-step output paths; job_list.py renders the status table shown by job-list and the UI.

Section 9

The Gradio front-end (facefusion/uis/) is a thin, self-wiring layer over the same state and job machinery the CLI uses. Layouts assemble components; components follow a uniform render/listen/update pattern.

9.1 Layouts & loading

uis/core.py dynamically imports a layout module (facefusion.uis.layouts.<name>) and asserts it implements the four layout methods pre_check, render, listen, run; a missing method hard-exits. Four layouts ship:

default

benchmark

launch() builds a gradio.Blocks with a custom theme/CSS, calls each layout's render() then listen() (wrapping in a Tab when more than one layout), and finally run(ui) which launches the server (with favicon and optional auto-open browser).

Section 10

Cross-Cutting Concerns & Appendices

10.1 The content-safety gate

Hash-pinned NSFW detector — do not edit content_analyser.py core.py::common_pre_check() re-hashes the source of content_analyser.py with crc32 and aborts startup unless it equals the literal b14e7b92. This runs before run, headless-run, batch-run, and benchmark. Any change to that file — even whitespace — changes the hash and makes every processing command hard-exit. If a refactor is unavoidable, the expected hash in common_pre_check must be updated to match.

Functionally, the content analyser is a three-model NSFW ensemble (EraX, Marqo, Freepik). A frame is flagged only on a 2-of-3 majority; a video is rejected when the positive-detection rate exceeds 10% of sampled frames (one frame per second). This is a deliberate safety mechanism, not incidental code.

10.2 Threading & concurrency model

Where parallelism lives
Frame-level: one ThreadPoolExecutor(execution_thread_count) in process_video. Within a frame, processors run sequentially. Multi-GPU spread is a random device-id choice per pool acquisition.
How correctness is preserved
thread_semaphore() (a global count-1 semaphore) serializes non-thread-safe OpenCV capture and some ONNX runs. conditional_thread_semaphore() narrows this to fragile backends only — DirectML (Win), MIGraphX / ROCm (Linux) — letting CUDA/CPU run inference concurrently.

10.4 Memory management

memory.py::limit_system_memory() caps the process working set — via SetProcessWorkingSetSize on Windows, setrlimit(RLIMIT_DATA) on POSIX. GPU memory is governed separately by the video_memory_strategy option (moderate/strict), which drives how aggressively processors clear inference pools in post_process. OMP_NUM_THREADS=1 is set for ONNX stability.
